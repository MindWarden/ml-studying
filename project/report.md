## 2. Постановка задачи и контекст

### 2.1. Предметная область
Удержание клиентов в телеком-индустрии. Привлечение нового клиента в среднем в 5–7 раз дороже, чем удержание существующего, поэтому раннее выявление клиентов с высокой вероятностью ухода — ключевая бизнес-метрика. Пользователь сервиса — система маркетинговых кампаний (CRM), которая для каждого клиента периодически запрашивает вероятность оттока и при превышении порога инициирует кампанию удержания.

### 2.2. Формулировка задачи в терминах ML
- **Тип задачи:** бинарная классификация.
- **Входные данные:** профиль клиента (19 признаков): демография (gender, SeniorCitizen, Partner, Dependents), параметры подключения (tenure, услуги PhoneService/InternetService и т.д.), коммерция (Contract, PaperlessBilling, PaymentMethod, MonthlyCharges, TotalCharges).
- **Выход:** вероятность ухода `[0, 1]` и бинарный класс по порогу, подобранному при обучении.
- **Ограничения:** модель должна работать на CPU за <100 мс на запрос; желательна интерпретируемость (бизнесу важно понимать, какие признаки влияют на риск).

### 2.3. Целевые метрики
- **ROC-AUC** — основная: устойчива к дисбалансу классов (Churn=1 ~26.5%), измеряет качество ранжирования клиентов по риску.
- **Recall** — ключевая для бизнес-сценария: пропустить уходящего клиента (FN) дороже, чем потратить кампанию удержания на лояльного (FP).
- **F2** — агрегирующая метрика для подбора порога: как F1, но recall весит вдвое больше precision — формализует асимметрию цены ошибок.
- **F1, Precision, Accuracy** — справочно.

## 3. Данные

### 3.1. Источник
Открытый датасет [Telco Customer Churn](https://github.com/IBM/telco-customer-churn-on-icp4d/blob/master/data/Telco-Customer-Churn.csv) от IBM. Свободно доступен на GitHub, классический ориентир для задачи churn. Персональных данных не содержит.

### 3.2. Структура данных
- 7043 строки, 21 колонка.
- 4 числовых признака: `tenure`, `MonthlyCharges`, `TotalCharges`, `SeniorCitizen` (последний бинарный).
- 15 категориальных признаков (gender, Contract, PaymentMethod и т.д.).
- 1 идентификатор (`customerID` — удаляется).
- 1 целевая переменная (`Churn`).

### 3.3. Предобработка и EDA
Полный анализ — в `notebooks/01_eda.ipynb`. Ключевые наблюдения:

1. **`TotalCharges` приходит строкой**, потому что для клиентов с `tenure=0` в CSV стоят пробелы (11 строк). Конвертация: `pd.to_numeric(..., errors='coerce')` + `fillna(0.0)`.
2. **Дисбаланс классов:** Churn=Yes у 26.5% клиентов. Обоснование выбора метрик: accuracy ввела бы в заблуждение. В классических моделях используется `class_weight='balanced'`.
3. **Самые сильные сигналы оттока:**
   - `Contract = Month-to-month` → churn rate ~43% (vs ~3% у Two year).
   - `tenure` → новые клиенты (tenure < 12) уходят значительно чаще.
   - `OnlineSecurity = No`, `TechSupport = No` → выше отток.
   - `PaymentMethod = Electronic check` → выше отток.
   - `InternetService = Fiber optic` → выше отток (вероятно, дороже и больше жалоб на качество).
4. **Пропусков нет** после очистки.

### 3.4. Препроцессор
`ColumnTransformer`:
- Числовые признаки → `StandardScaler`.
- Категориальные → `OneHotEncoder(handle_unknown='ignore')`.

Сплит: 80% train / 20% test, **стратифицированный по `Churn`**, `random_state=42`. Тест не участвует ни в выборе модели, ни в подборе порога — используется только для финальной оценки.

## 4. Модели и эксперименты

### 4.1. Базовые модели (baseline)
Три классические модели с параметрами из `configs/config.yaml`, все — внутри одного `Pipeline` с препроцессором:

1. **Logistic Regression** — линейный baseline, `class_weight='balanced'`, `max_iter=1000`.
2. **Random Forest** — `n_estimators=200, max_depth=12, class_weight='balanced'`.
3. **Gradient Boosting** — `n_estimators=200, max_depth=3, learning_rate=0.1`.

### 4.2. Улучшенные модели: тюнинг гиперпараметров и нейросетевой бейзлайн
Поверх бейзлайнов — `GridSearchCV` (5-fold `StratifiedKFold`, scoring=ROC-AUC), сетки заданы в `configs/config.yaml`:

- **LogReg:** `C ∈ {0.01, 0.1, 1, 10}` → лучшее `C=10`.
- **RandomForest:** `n_estimators ∈ {200, 400}`, `max_depth ∈ {8, 12, 16}`, `min_samples_leaf ∈ {1, 3}` → лучшее `max_depth=8, min_samples_leaf=3, n_estimators=400`.
- **GradientBoosting:** `n_estimators ∈ {100, 200, 300}`, `learning_rate ∈ {0.05, 0.1}`, `max_depth ∈ {2, 3}` → лучшее `learning_rate=0.05, max_depth=2, n_estimators=200` (более мелкие деревья с меньшим шагом — меньше переобучение).
- **MLP (нейросетевой бейзлайн):** `MLPClassifier` поверх того же препроцессора, `hidden_layer_sizes ∈ {(64,32), (128,64)}`, `alpha ∈ {1e-3, 1e-2}`, `early_stopping=True` → лучшее `(128,64), alpha=0.01`.

Вывод по нейросети: MLP достигает ROC-AUC ≈ 0.840 — на уровне линейной модели, но хуже бустинга. Для табличных данных объёмом ~7 тыс. строк это ожидаемо: преимущества нейросетей не реализуются, а стоимость (время обучения, подбор архитектуры, непрозрачность) выше.

### 4.3. Трекинг экспериментов
Все прогоны (3 baseline + 4 tuned + финальный) логируются в **MLflow** (локальный файловый бэкенд `mlruns/`, эксперимент `telco-churn`): параметры моделей, CV- и test-метрики. Полный прогон воспроизводится одной командой `python -m src.models.train`.

## 5. Экспериментальный протокол и результаты

### 5.1. Протокол
- Один стратифицированный split 80/20 (`random_state=42`) для всех моделей: train 5634 объекта, test 1409, churn rate 26.5% в обеих частях.
- Выбор лучшей модели — по **кросс-валидационному ROC-AUC на train** (5-fold StratifiedKFold), тест в выборе не участвует.
- Порог классификации подбирается **на out-of-fold предсказаниях train** (максимизация F2), тест снова не участвует.
- Все метрики ниже — на тесте.

### 5.2. Сравнение моделей

| Модель / конфигурация | CV ROC-AUC | ROC-AUC | F1 | F2 | Precision | Recall | Accuracy |
|---|---|---|---|---|---|---|---|
| baseline LogReg | — | 0.842 | 0.614 | 0.705 | 0.504 | 0.783 | 0.738 |
| baseline RandomForest | — | 0.834 | 0.604 | 0.629 | 0.567 | 0.647 | 0.775 |
| baseline GradientBoosting | — | 0.835 | 0.565 | 0.531 | 0.632 | 0.511 | 0.791 |
| tuned LogReg (C=10) | 0.846 | 0.841 | 0.615 | 0.706 | 0.506 | 0.783 | 0.740 |
| tuned RandomForest | 0.847 | 0.842 | 0.632 | 0.715 | 0.530 | 0.783 | 0.758 |
| **tuned GradientBoosting** | **0.850** | **0.846** | 0.571 | 0.530 | 0.656 | 0.505 | 0.798 |
| tuned MLP (128-64) | 0.844 | 0.840 | 0.529 | 0.471 | 0.667 | 0.438 | 0.793 |
| **tuned GB + порог 0.14** | 0.850 | 0.846 | 0.586 | **0.738** | 0.436 | **0.893** | 0.664 |

Точные значения — в `artifacts/metrics.json` и MLflow (`mlruns/`).

### 5.3. Подбор порога классификации
У лучшей по ранжированию модели (tuned GradientBoosting) при стандартном пороге 0.5 recall лишь 0.51 — она «осторожна» и пропускает половину уходящих клиентов. Вместо смены модели подобран **порог 0.14**, максимизирующий F2 на out-of-fold предсказаниях train (F2: 0.545 → 0.750 на OOF). На тесте recall вырос с 0.51 до **0.89** при precision 0.44.

### 5.4. Выбор финальной модели

**Финальная конфигурация: GradientBoosting (learning_rate=0.05, max_depth=2, n_estimators=200) + порог 0.14.**

Обоснование:
1. **Лучшее ранжирование:** максимальный CV ROC-AUC (0.850) и test ROC-AUC (0.846) среди всех семи конфигураций — для CRM-сценария (топ-N клиентов на кампанию удержания) качество ранжирования первично.
2. **Recall 0.89 за счёт порога, а не смены модели:** порог — свободный параметр продукта; его подбор под F2 дал максимальный recall среди всех конфигураций при сохранении лучшего AUC.
3. **Trade-off осознан:** precision 0.44 означает, что больше половины кампаний уйдёт «впустую», но стоимость кампании (письмо/скидка) на порядок ниже потери клиента; при изменении экономики порог перенастраивается без переобучения (env `CHURN_THRESHOLD`).
4. **Альтернативы:** tuned RandomForest даёт сбалансированный профиль (F1 0.632) без подбора порога, но проигрывает по AUC и recall; MLP не оправдал усложнения.

## 6. Архитектура решения и сервис

### 6.1. Пайплайн
```
CSV → load_clean (приведение типов, target Yes/No → 1/0)
    → train_test_split_stratified (80/20)
    → базовые модели + GridSearchCV (LogReg / RF / GB / MLP)   → MLflow (mlruns/)
    → выбор лучшей по CV ROC-AUC
    → подбор порога по F2 (out-of-fold)
    → artifacts/model.pkl (Pipeline) + threshold.json + metrics.json
                                     │
                                     ▼
                       FastAPI (lifespan = load model)
                            │
                  ┌─────────┴──────────┐
                  ▼                    ▼
              GET /health        POST /predict
```

В сервисе используется **тот же `Pipeline`** (препроцессор + модель), сохранённый одним объектом, — несоответствия preprocessing между обучением и инференсом исключены. Порог сервис читает из `artifacts/threshold.json` (переопределяется переменной окружения `CHURN_THRESHOLD`).

### 6.2. API

**`GET /health`** → `{"status": "ok", "model_loaded": true}`

**`POST /predict`** — принимает JSON со всеми 19 признаками клиента, валидируемый Pydantic-схемой `CustomerFeatures` со строгим типом для каждого категориального поля (`Literal[...]`, невалидное значение → 422). Возвращает:
```json
{"churn_probability": 0.811, "churn_class": "Yes", "threshold": 0.14}
```

**`GET /docs`** — автоматический Swagger UI с примерами запросов.

### 6.3. Стек
- Python 3.13 (зафиксирован в Docker через `python:3.13-slim`).
- pandas, numpy, scikit-learn, joblib — данные и модели.
- mlflow-skinny — трекинг экспериментов.
- FastAPI, Uvicorn, Pydantic — сервис.
- pytest, httpx — тесты (10 штук).
- Docker — упаковка и развёртывание.

Запуск: `docker build -t aie-churn . && docker run -p 8000:8000 aie-churn`. Модель обучается на этапе сборки образа (`RUN python -m src.models.train`) — сериализованный Pipeline гарантированно совместим с версиями библиотек контейнера, а благодаря фиксированному seed результат детерминирован.

## 7. Наблюдаемость, конфигурация и безопасность

### 7.1. Логи
Стандартный `logging` с уровнем `INFO`, форматом `[timestamp] [level] [logger]: message`. Логируются:
- старт сервиса, факт загрузки модели и действующий порог;
- каждый `/predict` (ключевые признаки + результат);
- ошибки с трейсбеком (`log.exception`).

`/health`-эндпоинт опрашивается и Docker `HEALTHCHECK`-инструкцией — контейнер сообщает о своём состоянии оркестратору.

### 7.2. Конфиги
- `configs/config.yaml` — данные, списки фич, параметры базовых моделей, сетки GridSearchCV, β для подбора порога. Обучение читает этот файл — эксперимент перенастраивается без правки кода.
- `configs/.env.example` — шаблон переменных окружения (host, port, log level, путь к модели, threshold).

Все внешние параметры сервиса читаются через `os.getenv(..., default)`.

### 7.3. Безопасность
- Реальный `.env` **не коммитится** (есть в `.gitignore`).
- В репозитории нет токенов, паролей, API-ключей.
- В логах нет PII: датасет открытый, идентификатор клиента удаляется ещё на этапе загрузки.

## 8. Ограничения и дальнейшая работа

**Ограничения:**
- модель обучена на статичном датасете 2017 года, концепт-дрифт не отслеживается;
- нет аутентификации сервиса (по требованиям курса не нужна, в проде потребуется);
- MLflow работает в локальном файловом режиме — для команды нужен общий tracking-сервер.

**Возможные улучшения (по убыванию приоритета):**
1. калибровка вероятностей (Platt/isotonic) — для честной интерпретации порога как вероятности;
2. CatBoost/XGBoost + SHAP-интерпретация предсказаний;
3. мониторинг дрифта данных (PSI по ключевым признакам) и метрики Prometheus в сервисе;
4. периодическое переобучение по расписанию (Airflow/cron) с автоматическим сравнением с прод-моделью.

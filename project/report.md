## 2. Постановка задачи и контекст

### 2.1. Предметная область
Удержание клиентов в телеком-индустрии. Привлечение нового клиента в среднем в 5–7 раз дороже, чем удержание существующего, поэтому раннее выявление клиентов с высокой вероятностью ухода — ключевая бизнес-метрика. Пользователь сервиса — система маркетинговых кампаний (CRM), которая для каждого клиента периодически запрашивает вероятность оттока и при превышении порога инициирует кампанию удержания.

### 2.2. Формулировка задачи в терминах ML
- **Тип задачи:** бинарная классификация.
- **Входные данные:** профиль клиента (19 признаков): демография (gender, SeniorCitizen, Partner, Dependents), параметры подключения (tenure, услуги PhoneService/InternetService и т.д.), коммерция (Contract, PaperlessBilling, PaymentMethod, MonthlyCharges, TotalCharges).
- **Выход:** вероятность ухода `[0, 1]` и бинарный класс по порогу 0.5.
- **Ограничения:** модель должна работать на CPU за <100 мс на запрос; интерпретируемость (важно для бизнеса — нужно понимать, какие признаки влияют на риск).

### 2.3. Целевые метрики
- **ROC-AUC** — основная: устойчива к дисбалансу классов (Churn=1 ~26.5%), измеряет качество ранжирования.
- **F1** — баланс precision и recall.
- **Recall** — важная для задачи: пропустить уходящего клиента дороже, чем сделать ложноположительный прогноз.
- **Precision, Accuracy** — справочно.

## 3. Данные

### 3.1. Источник
Открытый датасет [Telco Customer Churn](https://github.com/IBM/telco-customer-churn-on-icp4d/blob/master/data/Telco-Customer-Churn.csv) от IBM. Свободно доступен на GitHub, классический ориентир для задачи churn.

### 3.2. Структура данных
- 7043 строки, 21 колонка.
- 4 числовых признака: `tenure`, `MonthlyCharges`, `TotalCharges`, `SeniorCitizen` (последний бинарный).
- 15 категориальных признаков (gender, Contract, PaymentMethod и т.д.).
- 1 идентификатор (`customerID` — удаляется).
- 1 целевая переменная (`Churn`).

### 3.3. Предобработка и EDA
Полный анализ — в `notebooks/01_eda.ipynb`. Ключевые наблюдения:

1. **`TotalCharges` приходит строкой**, потому что для клиентов с `tenure=0` в CSV стоят пробелы (11 строк). Конвертация: `pd.to_numeric(..., errors='coerce')` + `fillna(0.0)`.
2. **Дисбаланс классов:** Churn=Yes у 26.5% клиентов. Обоснование выбора метрик: accuracy ввела бы в заблуждение. В моделях используется `class_weight='balanced'`.
3. **Самые сильные сигналы оттока:**
   - `Contract = Month-to-month` → churn rate ~43% (vs 3% у Two year).
   - `tenure` → новые клиенты (tenure < 12) уходят значительно чаще.
   - `OnlineSecurity = No`, `TechSupport = No` → выше отток.
   - `PaymentMethod = Electronic check` → выше отток.
   - `InternetService = Fiber optic` → выше отток (вероятно, дороже и больше жалоб на качество).
4. **Пропусков нет** после очистки.

### 3.4. Препроцессор
`ColumnTransformer`:
- Числовые признаки → `StandardScaler`.
- Категориальные → `OneHotEncoder(handle_unknown='ignore')`.

Сплит: 80% train / 20% test, **стратифицированный по `Churn`**, `random_state=42`.

## 4. Модели и подходы

### 4.1. Baseline и улучшенные модели
Все три модели обучаются на одинаковом препроцессированном представлении (через `Pipeline`):

1. **Logistic Regression** — линейный baseline, `class_weight='balanced'`, `max_iter=1000`.
2. **Random Forest** — `n_estimators=200, max_depth=12, class_weight='balanced'`.
3. **Gradient Boosting** — `n_estimators=200, max_depth=3, learning_rate=0.1`.

Все эксперименты воспроизводимы запуском `python -m src.models.train`. Сравнительный анализ — в `notebooks/02_models_comparison.ipynb`.

### 4.2. Нейросети
Не использовались. Для этого датасета размером 7000 строк и 19 признаков преимущества нейросетей над градиентными бустингами/линейными моделями не ожидается; добавили бы сложность без выигрыша по метрикам. По FAQ курса это допустимо.

## 5. Экспериментальный протокол и результаты

### 5.1. Протокол
- Один и тот же стратифицированный split (80/20, seed=42) для всех моделей.
- Все метрики считаются на test (1409 объектов, churn rate 26.54%).
- Train: 5634 объекта, churn rate 26.54%.

### 5.2. Сравнение моделей

| Модель                | ROC-AUC | F1     | Precision | Recall | Accuracy |
|-----------------------|---------|--------|-----------|--------|----------|
| **LogisticRegression**| **0.842** | 0.614 | 0.504 | **0.783** | 0.738 |
| RandomForest          | 0.834   | 0.604  | 0.567     | 0.647  | 0.775    |
| GradientBoosting      | 0.835   | 0.565  | 0.632     | 0.511  | 0.791    |

Точные значения — в `artifacts/metrics.json`.

### 5.3. Выбор финальной модели

**Финальная модель: Logistic Regression с `class_weight='balanced'`.**

Обоснование:
1. **Лучший ROC-AUC** (0.842 против 0.834–0.835 у конкурентов) — модель лучше ранжирует клиентов по риску, что критично для CRM-сценария (топ-N кампаний удержания).
2. **Самый высокий recall** (0.78) — модель ловит 78% уходящих клиентов, тогда как RandomForest ловит 65%, а GradientBoosting — только 51%. Для бизнеса это важнее accuracy: пропустить уходящего клиента дороже, чем потратить кампанию удержания на лояльного.
3. **Интерпретируемость** — линейные коэффициенты можно объяснить бизнес-стейкхолдерам, что важно для построения CRM-логики (отдел маркетинга должен понимать триггеры).
4. **Скорость и простота** — инференс <1 мс, модель сериализуется в небольшой `model.pkl`, поддержка тривиальна.

Trade-off: GradientBoosting даёт чуть выше accuracy и precision, но проигрывает по recall и AUC. Для нашей задачи (раннее обнаружение ухода) recall важнее. Если бы стоимость ложноположительной кампании была высокой — выбрали бы GradientBoosting и подняли бы threshold.

## 6. Архитектура решения и сервис

### 6.1. Пайплайн
```
CSV → load_clean (приведение типов, target Yes/No → 1/0)
    → train_test_split_stratified
    → ColumnTransformer (StandardScaler + OneHotEncoder)
    → LogisticRegression
    → joblib.dump → artifacts/model.pkl
                                     │
                                     ▼
                       FastAPI (lifespan = load model)
                            │
                  ┌─────────┴──────────┐
                  ▼                    ▼
              GET /health        POST /predict
```

В сервисе используется **тот же `Pipeline`** (препроцессор + модель), сохранённый одним объектом, — поэтому несоответствия preprocessing между обучением и инференсом исключены.

### 6.2. API

**`GET /health`** → `{"status": "ok", "model_loaded": true}`

**`POST /predict`** — принимает JSON со всеми 19 признаками клиента, валидируемый Pydantic-схемой `CustomerFeatures` с строгим типом для каждого категориального поля (`Literal[...]`). Возвращает:
```json
{"churn_probability": 0.806, "churn_class": "Yes", "threshold": 0.5}
```

**`GET /docs`** — автоматический Swagger UI с примерами запросов.

### 6.3. Стек
- Python 3.13 (зафиксирован в Docker через `python:3.13-slim`).
- pandas, numpy, scikit-learn, joblib — данные и модель.
- FastAPI, Uvicorn, Pydantic — сервис.
- pytest, httpx — тесты.
- Docker — упаковка и развёртывание (один `Dockerfile` собирает образ за минуту).

Запуск: `docker build -t aie-churn . && docker run -p 8000:8000 aie-churn`.

## 7. Наблюдаемость, конфигурация и безопасность

### 7.1. Логи
Стандартный `logging` с уровнем `INFO`, форматом `[timestamp] [level] [logger]: message`. Логируются:
- старт сервиса и факт загрузки модели;
- каждый `/predict` (ключевые признаки + результат);
- ошибки с трейсбеком (`log.exception`).

`/health`-эндпоинт доступен и из Docker `HEALTHCHECK`-инструкции — контейнер сообщает о своём состоянии.

### 7.2. Конфиги
- `configs/config.yaml` — параметры обучения (списки фич, гиперпараметры моделей, размер test_size).
- `configs/.env.example` — шаблон переменных окружения (host, port, log level, путь к модели, threshold).

Все внешние параметры сервиса читаются через `os.getenv(..., default)` — можно перенастроить без правки кода.

### 7.3. Безопасность
- Реальный `.env` **не коммитится** (есть в `.gitignore`).
- В репозитории нет токенов, паролей, API-ключей.
- Используемый датасет — открытый, без персональных данных.

## 8. Ограничения и дальнейшая работа

**Ограничения:**
- модель обучена на статичном датасете 2017 года, концепт-дрифт не отслеживается;
- threshold классификации фиксирован 0.5 (можно менять через ENV, но без автоматического подбора);
- нет аутентификации сервиса.

**Возможные улучшения (по убыванию приоритета):**
1. подбор threshold под максимизацию F-beta с β > 1 (приоритет recall);
2. тюнинг гиперпараметров (`GridSearchCV` или `Optuna`);
3. модели CatBoost/XGBoost + SHAP-интерпретация;
4. трекинг экспериментов через MLflow;
5. метрики Prometheus в сервисе и Grafana-дашборд;
6. кэширование результатов на уровне приложения.

# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использован датасет `S12-hw-dataset.csv` (часовые наблюдения, 4320 точек, январь--июнь 2025). Прогнозировалось следующее значение колонки `target`.
- Данные разбиты на `train / validation / test` по времени (70/15/15%).
- Сравнивались 4 подхода: B1 (naive-last), B2 (moving-average), B3 (Ridge на лаговых/rolling/календарных признаках), R1 (GRU на оконном представлении).
- Лучшим по validation MAE оказался R1 (GRU-forecast) с MAE = 5.29, что на 12% лучше Ridge и на 18% лучше naive baseline.

## 2. Среда и воспроизводимость

- Python: 3.14
- pandas / numpy / scikit-learn: актуальные версии
- torch: 2.x
- Устройство (CPU/GPU): CPU
- Seed: 42 (random, numpy, torch)
- Как запустить: открыть `HW12.ipynb` и выполнить Run All.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: часовая (1 наблюдение в час)
- Горизонт прогноза: 1 шаг (следующий час)
- Размер датасета: 4320 наблюдений
- Диапазон дат: 2025-01-01 00:00 -- 2025-06-29 23:00
- Есть ли дополнительные внешние признаки: нет, только `date` и `target`
- Комментарий: ряд демонстрирует выраженную суточную сезонность (значения растут днём и снижаются ночью) и лёгкий положительный тренд. Явных выбросов и пропусков не обнаружено. Ряд достаточно регулярный, что делает его подходящим для прогнозирования лаговыми и рекуррентными методами.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: строго по хронологии, без перемешивания.
- Какие доли или интервалы использовались: train = 70% (3024 точки), validation = 15% (648 точек), test = 15% (648 точек).
- Почему `random split` здесь некорректен: при случайном разбиении модель получает доступ к будущим наблюдениям в обучающей выборке, что нарушает причинно-следственную логику и завышает оценку качества (leakage). В реальной эксплуатации модель всегда прогнозирует будущее на основе прошлого.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: lag_1, lag_7, lag_14
- Какие rolling-признаки использовались: rolling_mean_7, rolling_std_7 (с shift(1) для предотвращения утечки текущего значения)
- Какие календарные признаки использовались: dayofweek, hour, dow_sin, dow_cos, hour_sin, hour_cos
- Как обрабатывались пропуски после построения лагов/rolling: строки с NaN удалены (первые ~14 наблюдений)
- Использовалось ли масштабирование и где именно оно обучалось: StandardScaler, fit только на train

## 5. Модели и эксперименты (B1, B2, B3, R1)

- B1 (`naive-last`): прогноз = последнее известное значение (lag_1). Самый простой baseline.
- B2 (`moving-average`): прогноз = скользящее среднее за 7 предыдущих значений (rolling_mean_7). Усредняет шум, но сильно запаздывает.
- B3 (`ridge-lag-features`): Ridge-регрессия (alpha=1.0) на 11 признаках (лаги, rolling-статистики, календарные). Масштабирование StandardScaler, fit на train.
- R1 (`gru-forecast`): GRU (hidden_size=64, num_layers=2, dropout=0.1) на оконном представлении ряда длиной 48 часов.

Дополнительно:

- Основная метрика выбора лучшей модели: MAE на validation
- Дополнительные метрики: RMSE, MAPE
- `window_size` для `GRU`: 48 (2 суток)
- Batch size: 64
- Максимальное число эпох: 30
- Optimizer: Adam
- Learning rate: 5e-4
- Как сохранялась лучшая модель: по минимальному val_loss (MSE), восстановление state_dict лучшей эпохи

## 7. Анализ

Naive baseline (B1) показал val_MAE = 6.44, что является неплохим результатом для часовых данных с умеренной волатильностью -- предыдущее часовое значение уже содержит значительную информацию о следующем.

Moving-average (B2) с окном 7 оказался заметно хуже (val_MAE = 12.72), поскольку усреднение за 7 часов сильно сглаживает суточные колебания и запаздывает за быстрыми изменениями ряда.

Ridge на признаках (B3) улучшил результат до val_MAE = 6.03, используя комбинацию лагов разных горизонтов (1, 7, 14 часов) и календарных признаков (час суток, день недели). Это позволило модели учитывать суточную периодичность.

GRU (R1) достигла лучшего результата по validation (MAE = 5.29), что объясняется способностью рекуррентной модели выучивать нелинейные зависимости во временном окне из 48 часов. Два слоя GRU с hidden_size=64 обеспечили достаточную ёмкость модели.

Суточная сезонность -- основной драйвер качества: модели, учитывающие час суток (B3, R1), существенно превосходят те, которые этого не делают (B2). Тренд слабый и не создаёт серьёзных проблем для прогнозирования.

Потенциальные утечки данных в такой задаче: использование rolling-статистик без shift (текущее значение попадает в среднее), масштабирование по всему датасету вместо только train, случайное разбиение вместо temporal split.

Выбор по validation принципиален: если бы мы выбирали модель по test, то занизили бы оценку ошибки генерализации и могли бы переоценить качество подхода.

На test GRU показала MAE = 6.25, что немного хуже, чем на validation (5.29). Это нормально и может объясняться сдвигом распределения данных во времени.

## 8. Итоговый вывод

Для задачи часового прогнозирования данного ряда GRU оказалась лучшей моделью по validation, обойдя Ridge на признаках и простые baseline. Однако разница между Ridge (B3) и GRU (R1) на test минимальна (6.10 vs 6.25), что говорит о том, что для производственного использования Ridge с хорошими признаками может быть предпочтительнее из-за простоты, интерпретируемости и скорости.

Переход к GRU/нейросетям оправдан, когда ряд содержит сложные нелинейные паттерны, которые не схватываются линейными моделями на ручных признаках, или когда есть достаточно данных для обучения.

Главное, что стало очевидным про корректную валидацию: temporal split -- обязательное условие для честной оценки моделей на временных рядах. Random split создаёт ложное ощущение высокого качества за счёт утечки информации из будущего в прошлое.

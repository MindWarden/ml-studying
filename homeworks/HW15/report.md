# Отчёт HW15 — Сравнение режимов работы instruction-LLM

## 1. Постановка задачи

Цель работы — на одной и той же прикладной задаче текстовой классификации сравнить три инженерных режима применения компактной instruction-LLM:

1. **zero-shot** — только системная инструкция, без обучающих примеров;
2. **few-shot** — в промпт добавлены несколько размеченных примеров;
3. **LoRA-адаптация** — компактный fine-tuning части весов модели.

> Семинар 15 сам по себе не предполагает обязательной домашней работы (см. `FORYOU/S15-brief.md`). Данная работа оформлена как инициативное учебное упражнение по материалам demo-01/02/03.

**Задача.** Классификация коротких пользовательских сообщений в онлайн-сервисе на 4 класса: `bug`, `feature`, `question`, `praise`.

**Модель.** `Qwen/Qwen2.5-0.5B-Instruct` — компактная instruct-LLM, запускается на CPU, LoRA-шаг ускоряется на GPU.

## 2. Данные

Собран размеченный датасет из 60 коротких русскоязычных сообщений, по 15 на каждый класс. Примеры сформированы вручную так, чтобы в каждом классе были как однозначные, так и пограничные кейсы (например, «Нужна поддержка нескольких валют» — феча, но формулировка близка к вопросу).

Стратифицированный split: **40 train / 20 test** (по 10/5 на класс).

- Артефакт: [`artifacts/dataset_overview.csv`](artifacts/dataset_overview.csv)

## 3. Подход

### 3.1. Промпт

Единый системный промпт для всех трёх режимов:

> «Ты классификатор пользовательских сообщений. Определи класс сообщения из ровно 4 вариантов: bug, feature, question, praise. Отвечай ОДНИМ словом из этого списка, без пояснений и лишних символов.»

### 3.2. Режимы

- **zero-shot**: system + user.
- **few-shot**: system + k примеров в формате `user/assistant` + user. Основной прогон k=4 (по одному примеру на класс), дополнительно sweep по k ∈ {0, 2, 4, 8}.
- **LoRA**: `r=8`, `alpha=16`, `dropout=0.05`, target `q_proj, v_proj`, 3 эпохи, lr=2e-4. Обучение на 40 train-примерах в instruct-формате с маскировкой `labels = input_ids`.

### 3.3. Парсер ответа

Из сгенерированного текста ищем вхождение одного из четырёх меток. Если ни одна не найдена — ответ считается не распарсенным.

### 3.4. Метрики

- `accuracy`;
- `macro F1` (сбалансированное качество по классам);
- `parse_rate` — доля ответов, из которых удалось извлечь одну из четырёх меток.

## 4. Результаты

### 4.3. Анализ ошибок по типам

| тип ошибки             | zero-shot | few-shot k=4 | LoRA |
|------------------------|-----------|--------------|------|
| `bug` → `question`     | 1         | 0            | 0    |
| `feature` → `question` | 1         | 1            | 0    |
| `praise` → `feature`   | 0         | 1            | 1    |
| `question` → `bug`     | 1         | 0            | 0    |
| нарушение формата      | 1         | 0            | 0    |

Комментарии:

- **zero-shot** стабильно теряет часть ответов из-за формата (дописывает пояснения) и путает нейтрально сформулированные баги с вопросами.
- **few-shot** полностью убирает ошибки формата, но граница `feature`/`question` остаётся размытой («нужна X» читается и как просьба, и как вопрос).
- **LoRA** снимает путаницу `feature`/`question`, но оставляет один пограничный кейс `praise` → `feature` (короткая похвала без эмоциональных маркеров).

- Артефакт: [`artifacts/error_analysis.csv`](artifacts/error_analysis.csv)

## 5. Выводы

1. **Zero-shot даёт разумный старт**, но непригоден для строгого инженерного использования: регулярно нарушает формат и путает близкие классы.
2. **Few-shot (k=4) — самый выгодный шаг по цене/качеству**. Без обучения модели, одним промптом, мы закрыли ошибки формата и довели `accuracy` до 0.90. Дальнейшее увеличение k не помогает.
3. **LoRA даёт дополнительный +0.05 accuracy** и максимальную стабильность формата. Основная ценность — не точность, а предсказуемость на пограничных кейсах.
4. **Инженерная логика выбора режима:**
   - простая таксономия + контролируемый формат → достаточно `few-shot`;
   - важна устойчивость, доменные нюансы, повторяемость → `LoRA`;
   - полный fine-tuning в учебной задаче такого масштаба не оправдан.

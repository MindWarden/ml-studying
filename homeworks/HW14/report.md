# HW14 – эмбеддинги, FAISS, оценка retrieval и mini-RAG по базе знаний

## 1. Кратко: что сделано

- Собрана база знаний из 20 документов о Солнечной системе (планеты, спутники, другие объекты).
- Документы разбиты на 55 чанков (chunk_size=30, overlap=10 слов).
- Использована мультиязычная embedding-модель `paraphrase-multilingual-MiniLM-L12-v2`.
- Построен индекс FAISS (IndexFlatIP) для поиска по cosine similarity.
- Retrieval показал hit@5=1.00, recall@5=1.00, MRR@5=0.95 на 10 контрольных запросах.
- После добавления 3 новых документов (Энцелад, Церера, Вояджеры) retrieval корректно обновился — все 5 тестовых запросов изменили результаты.
- Собран mini-RAG с шаблонным генератором ответов и возвратом источников.

## 2. Среда и воспроизводимость

- Python: 3.14.0
- faiss / faiss-cpu: 1.13.2
- sentence-transformers: 5.4.0
- torch: 2.11.0+cpu
- Устройство (CPU/GPU): CPU
- Seed: 42
- Как запустить: открыть `HW14.ipynb` и выполнить Run All.

## 3. База знаний и подготовка документов

- Предметная область: Солнечная система (планеты, спутники, астероиды, кометы, космические аппараты).
- Источник документов: собственная подборка фактографических описаний.
- Число исходных документов: 20 (до обновления), 23 (после обновления).
- Число чанков после разбиения: 55 (до обновления), 63 (после обновления).
- Какой способ чанкинга использовался: разбиение по словам с перекрытием.
- Основные параметры чанкинга: chunk_size=30 слов, overlap=10 слов.
- Комментарий: тема Солнечной системы хорошо подходит для retrieval — каждый документ описывает отдельный объект с уникальными фактами (температуры, размеры, спутники, особенности), что позволяет чётко привязать вопросы к конкретным документам. Документы достаточно содержательны для вопросов, но при этом компактны для учебного pipeline. Mini-RAG по такой базе позволяет отвечать на фактографические вопросы с указанием источников.

## 4. Retrieval и индекс

### 4.1. Эмбеддинги и индекс

- Какая embedding-модель или способ векторизации использовались: `paraphrase-multilingual-MiniLM-L12-v2` (sentence-transformers), мультиязычная модель, 384 измерения.
- Какая метрика сходства использовалась: cosine similarity (через inner product нормализованных векторов).
- Какой индекс `FAISS` использовался: IndexFlatIP (точный поиск по скалярному произведению).
- Какой `top_k` использовался по умолчанию: 5.
- Что показали первые примеры retrieval: модель корректно находит документы по смыслу запроса — даже если запрос и документ используют разные формулировки (например, «ближайшая к Солнцу» → документ о Меркурии).

### 4.2. Контрольные запросы и оценка retrieval

- Сколько контрольных запросов использовалось: 10.
- Что считалось релевантным ответом: хотя бы один чанк из ожидаемого документа (doc_id) попал в top-k.
- Какие метрики retrieval считались: hit@k, recall@k, MRR@k.
- Итоговый `hit@5`: 1.00.
- Итоговый `recall@5`: 1.00.
- Дополнительные метрики: MRR@5 = 0.95.
- Какие запросы оказались самыми простыми: запросы с прямым упоминанием ключевых слов из документа (например, «Большое Красное Пятно Юпитера»).
- Какие запросы оказались самыми проблемными: запросы, требующие косвенных связей (например, «Программа Аполлон Луна» — слово «Аполлон» не является названием объекта).

## 5. Эксперимент по параметрам retrieval и обновление базы знаний

- Какой параметр сравнивался: chunk_size (30 vs 50 слов).
- Какие два варианта сравнивались: chunk_size=30/overlap=10 (55 чанков) и chunk_size=50/overlap=15 (35 чанков).
- Как изменилось качество retrieval: при chunk_size=30 MRR@5=0.95, при chunk_size=50 MRR@5=0.87. Hit@5 и recall@5 остались 1.00 в обоих случаях.
- Какой вариант выбрали как основной и почему: chunk_size=30 — более высокий MRR@5 означает, что релевантный документ чаще оказывается на первой позиции.
- Что именно было обновлено в базе знаний: добавлены 3 новых документа — Энцелад (спутник Сатурна), Церера (карликовая планета) и Вояджеры (межпланетные зонды).
- Как была выполнена переиндексация: полный пересчёт чанкинга, эмбеддингов и построение нового индекса FAISS.
- Что изменилось в retrieval после обновления базы знаний: все 5 тестовых запросов изменили результаты — новые документы корректно появились в top-k для релевантных запросов (например, запрос о гейзерах на спутнике Сатурна стал находить документ об Энцеладе).

## 6. Mini-RAG и результаты

Ссылки на файлы в репозитории:

- Оценка retrieval: `./artifacts/retrieval_eval.csv`
- Примеры ответов mini-RAG: `./artifacts/rag_examples.csv`
- Сравнение до/после обновления: `./artifacts/retrieval_before_after_update.csv`

Короткая сводка:

- Контекст формировался из top-3 найденных чанков, объединённых в единый текст.
- Генерация ответа: шаблонный генератор без LLM — из контекста извлекаются предложения, наиболее релевантные запросу (по пересечению слов), и объединяются в ответ.
- Источники возвращались вместе с ответом (название документа и doc_id).
- На каких вопросах mini-RAG сработал лучше всего: фактографические вопросы с однозначным ответом в одном документе (например, «Какая температура на Меркурии?»).
- На каких вопросах mini-RAG ошибался: вопросы вне области базы знаний (экзопланеты), вопросы о деталях, отсутствующих в базе (кто открыл Плутон), и запросы на сравнение нескольких объектов.
- Качество retrieval оказалось ключевым — шаблонный генератор лишь компилирует найденный контекст, поэтому если retrieval нашёл нужный документ, ответ получается адекватным.

## 7. Анализ

Выбранная база знаний о Солнечной системе оказалась удачной для учебного pipeline: документы тематически разнообразны, но принадлежат одной области, что позволяет формулировать осмысленные контрольные запросы. Каждый документ описывает уникальный объект, поэтому retrieval имеет чёткий ground truth.

Чанкинг с chunk_size=30 слов хорошо подошёл для наших коротких документов — при этом каждый чанк сохраняет достаточно контекста. Эксперимент с chunk_size=50 показал, что увеличение размера чанка снижает MRR (с 0.95 до 0.87), хотя hit@k остаётся идеальным. Это объясняется тем, что крупные чанки «размывают» семантический сигнал.

Формальная оценка retrieval (hit@k, recall@k, MRR@k) оказалась полезной для объективного сравнения параметров — без метрик было бы сложно обосновать выбор chunk_size. Обновление базы знаний наглядно показало, что система корректно реагирует на новые документы.

Наиболее показательные ошибки mini-RAG связаны с ограничениями шаблонного генератора и неполнотой базы знаний: система не может сказать «информация отсутствует» и вместо этого формирует ответ из нерелевантного контекста. Основное ограничение — отсутствие генеративной модели, которая могла бы синтезировать ответ из контекста, а не просто копировать предложения.

## 8. Итоговый вывод

Для учебной retrieval-задачи конвейер «sentence-transformers + FAISS IndexFlatIP» работает надёжно — мультиязычная модель paraphrase-multilingual-MiniLM-L12-v2 обеспечила hit@5=1.00 на 10 контрольных запросах по русскоязычной базе знаний. Качество retrieval — ключевой фактор для mini-RAG: даже простой шаблонный генератор даёт полезные ответы, если retrieval нашёл правильный фрагмент. Главный урок — качество retrieval определяется связкой «размер чанка + модель эмбеддингов», а не сложностью генератора ответов.
